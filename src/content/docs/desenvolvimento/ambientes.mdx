A Rede Nacional de Dados em Saúde (RNDS) oferece dois ambientes: homologação e produção. Cada um tem dois endereços, um
para autenticação (Auth) e outro para os serviços FHIR (EHR). Os endereços desta página foram conferidos no
[guia da RNDS](https://rnds-guia.saude.gov.br/docs/rnds/ambientes) em 28 de outubro de 2026.

## Qual ambiente usar

- **Homologação:** para desenvolvimento e testes. É único para todo o Brasil. O acesso é liberado quando o DATASUS
  aprova a solicitação de acesso feita pelo gestor no Portal de Serviços.
- **Produção:** para o envio real de dados. O acesso é liberado depois que o estabelecimento apresenta as evidências de
  homologação e o DATASUS aprova a solicitação de produção. Veja
  [Adesão e credenciamento](/fhir-ig/gestao/adesao-e-credenciamento/).

<Aside type="caution">
	O guia da RNDS é explícito: o ambiente de produção não deve ser usado para experimentar a integração. Todo teste vai para a
	homologação.
</Aside>

### O estado do CNES define o endpoint

O guia da RNDS diz que cada estabelecimento, "conforme o CNES em questão, fará uso do estado correspondente". O exemplo do
guia é um laboratório de Goiás (CNES 2337991), que usa `go-ehr-services.saude.gov.br`. Um laboratório de Minas Gerais usa
obrigatoriamente `mg-ehr-services.saude.gov.br`.

Na prática:

- A UF que decide é a do estabelecimento identificado pelo Cadastro Nacional de Estabelecimentos de Saúde (CNES), e não
  a do paciente nem a do servidor onde o seu sistema roda.
- Um sistema que atende estabelecimentos em várias UFs (rede de laboratórios, empresa de software com clientes em
  vários estados) escolhe o host por estabelecimento, a cada envio.
- O token obtido no endereço Auth é o mesmo para qualquer UF. O que muda é só o host EHR.

## Rede e firewall

A solicitação de acesso feita no Portal de Serviços do DATASUS pede a faixa de IPs dos servidores que farão as
chamadas. As recomendações a seguir são de engenharia (não são exigências publicadas pela RNDS):

- **Saída com IP fixo.** Faça as chamadas a partir de IPs de saída estáveis (NAT com IP elástico, proxy de saída) e
  informe esses IPs na solicitação. Em nuvem, IPs dinâmicos de funções serverless ou contêineres mudam sem aviso.
- **Atualize o cadastro antes de migrar.** Uma troca de provedor, de região ou de NAT muda o IP de saída. Peça a
  atualização ao DATASUS antes da migração.
- **Libere a saída HTTPS (porta 443)** para `ehr-auth-hmg.saude.gov.br` e `ehr-services.hmg.saude.gov.br` em homologação, e
  para `ehr-auth.saude.gov.br` e os hosts `<uf>-ehr-services.saude.gov.br` que você usa em produção.
- **Libere por nome, não por IP.** Os IPs dos servidores da RNDS não são publicados. Regras de firewall baseadas em IP de
  destino quebram quando a infraestrutura do Ministério muda.
- **Não intercepte o TLS do serviço Auth.** Proxies corporativos que fazem inspeção de TLS substituem o certificado de
  cliente e impedem a autenticação. Crie uma exceção para o host Auth.

## Boas práticas de configuração

- **Separe as configurações por ambiente.** Host Auth, host EHR, caminho do certificado e senha devem ser configuração,
  nunca código. Um erro comum é publicar em produção com o host de homologação, ou o contrário.
- **Mapeie UF para host em uma tabela.** Derive o host de produção da UF do estabelecimento. Não monte o host por
  concatenação de texto vindo do usuário.
- **Use o identificador do solicitante certo em cada ambiente.** O identificador do solicitante, atribuído pela RNDS no
  credenciamento, entra no `Bundle.identifier.system` de cada documento. Veja
  [Envio de documentos](/fhir-ig/desenvolvimento/envio-de-documentos/).
- **Guarde o certificado em cofre de segredos.** O certificado A1 e a senha dão acesso à RNDS em nome do estabelecimento.
  Veja [Autenticação](/fhir-ig/desenvolvimento/autenticacao/).
- **Registre qual ambiente e qual host responderam.** Inclua o host e o id devolvido pela RNDS nos logs de cada envio. Isso
  facilita a montagem das evidências de homologação e o suporte em produção.
